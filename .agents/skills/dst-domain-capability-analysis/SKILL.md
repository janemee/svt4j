# 业务域产品能力分析

本 skill 用来把现有后端服务代码中的业务能力，按领域建模方式整理成领域模块、子域和能力清单。

目标不是罗列接口，也不是照抄包结构，而是基于当前实现识别业务闭环、核心对象和能力边界。

## 适用场景

- 用户要梳理某个业务域的产品功能清单
- 用户要输出领域模块、子域、领域能力地图
- 用户明确要求“从代码现状出发”而不是从规划方案出发
- 仓库是总控仓，下面包含多个后端服务子仓（兼容 Java 及 PHP 等各类服务分析）
- 需要从后端服务实现梳理业务域能力

## 核心原则

1. API 入口只是索引，不是结论。
2. 包结构只是线索，不是领域边界。
3. 默认不分析前端项目。
4. 以当前代码现状归纳，不擅自扩展未来能力。
5. 领域必须相对完整、自闭环，不能把单个接口或单个动作抬升成领域。
6. 子域也必须相对独立，不能把一组零散接口动作误判成子域。
7. 末级能力不是必须层级；如果子域已经足够具体，就停在子域层。
8. 发现新旧并存、`old/new`、`bak/v2`、多端并存时，先判断关系，再决定是否纳入正式结构。
9. 剔除纯查询类内容：忽略不改变领域状态的读操作（如列表查询、详情获取、数据导出等），聚焦于业务状态变更和核心领域行为。

## 标准分析流程

### Step 1：先确认分析口径

开始前优先确认以下信息：

- 要分析哪个业务域
  - 是当前总控仓下的某个后端服务子仓，还是全部后端服务
- 输出目标
  - 是要领域地图、产品功能清单，还是汇报版模块清单
- 输出粒度
  - 只到一级领域，还是继续到子域、能力
- 时间口径
  - 按代码现状，还是按线上已发布能力

如果用户没有提供完整信息，默认以“全部后端服务 + 代码现状 + 领域建模归纳 + 逐层确认”为准。

### Step 2：建立初始线索，不直接下结论

先做轻量预扫，建立线索地图：

- 后端：`controller`、`innerapi`、`openapi`（若是 PHP 项目，则重点关注 `app/Http/Controllers` 等）
- 服务：`service`、核心实现类、状态机、核心实体（若是 PHP 项目，则重点关注 `app/Services`、`Models` 等）
- 文档：README、设计文档、术语表

这一步只回答：

- 可能有哪些一级业务块
- 哪些模块明显是技术支撑
- 哪些模块存在新旧并存
- 哪些模块边界可能混淆

不要在这一步直接输出正式领域清单。

### Step 3：先识别一级领域

一级领域判断必须同时满足尽量多的条件：

- 有明确核心业务对象
- 有相对完整的业务目标
- 有相对独立的状态或生命周期
- 有稳定输入输出边界
- 能在不依赖其他模块细节的情况下单独解释其业务价值

如果某个模块只有以下特征之一，通常不能单独成立为领域：

- 只是一个 API
- 只是一个查询页面
- 只是一个单点动作
- 只是内部接口出口
- 只是数据修复或公共支撑

一级领域输出后，先让用户确认，再继续下钻。

### Step 4：逐个领域深挖，不并行乱拆

每次只分析一个领域，顺序建议：

1. 核心对象
2. 关键 service
3. 状态流转 / 状态机
4. 关键动作
5. 详情聚合逻辑
6. 与其他模块的边界

分析目标不是“列出接口”，而是判断这个领域内部是否存在相对独立的业务分组。

### Step 5：识别子域

子域成立的判断标准：

- 有相对稳定的职责边界
- 有自己关注的对象或过程
- 有相对收敛的业务规则
- 不是纯粹的展示视图或接口出口

子域不应该只是这些东西：

- 列表、详情、新增、编辑
- PC / App / OpenAPI / InnerAPI
- 单个工单按钮动作
- 若干接口的机械归类

如果一个子域已经足够具体，且继续拆分只会变成接口动作列表，就停在子域层，不再往下拆。

### Step 6：只在必要时继续识别能力

只有当某个子域内部还能稳定拆出多个独立业务能力时，才继续输出末级能力。

可继续下钻的信号：

- 子域内同时存在结构管理、详情聚合、状态推进等不同职责
- 子域内同时存在发起、完成、撤销、同步等不同业务动作
- 子域内同时存在计划、执行、纠偏三类明显不同的业务面

不继续下钻的信号：

- 再拆就只剩 CRUD
- 再拆就只剩接口名
- 再拆就只剩页面动作

能力清单合并策略：
- 不要把颗粒度放得过细，如果存在大量碎片化的单点动作，需要进行业务维度的合并。
- 示例：将单点的状态流转动作（如：“已指派”、“改派”、“驳回”）合并归纳为更宏观的业务能力：“任务指派与流转管理”。

## 重点注意事项

### 1. 不要把实现分层当业务分层

以下内容通常不是独立业务领域：

- `common`
- `datarepair`
- `innerapi`
- `openapi`
- `app`
- `pc`

这些更像技术分层、出口分层或协同方式。

### 2. 不要把新旧并存模块直接合并

发现以下标记时，必须提高警惕：

- `Old`
- `New`
- `Bak`
- `V2`
- `Deprecated`
- 路由或页面中的“旧版/新版”

这类模块可能是：

- 升级替代
- 场景并存
- 过渡共存
- 历史遗留

未经用户确认，不要直接合并到正式结构。

### 3. 不要把“能力出口”当成业务子域

例如：

- App 接口
- 内部接口
- 开放平台接口

默认判断为同一业务能力的不同出口，而不是独立子域。只有当它们承载了明显不同的业务规则时，才可能单列。

### 4. 不要把单点能力抬升成领域

例如：

- 核销码
- 凭证生成
- 某一种工单
- 某一种通知

这类通常是某个领域或子域下的能力点，不是一级领域。

### 5. 不要为了凑结构强行拆三层

允许以下情况存在：

- 一级领域 + 子域
- 一级领域 + 子域 + 能力
- 一级领域直接停在若干具体子域

结构深度应由业务抽象是否成立决定，而不是由模板决定。

## 必须向用户确认的事项

出现以下情况时，必须显式向用户确认，再决定正式结构：

1. 新旧并存
   - 例如 `old/new`、`v1/v2`、`bak`
   - 需要确认是否属于升级替代

2. 历史模型与主模型并存
   - 需要确认哪个是正式口径，哪个是历史兼容

3. 多个模块边界高度重叠
   - 例如“资源需求 / 资源匹配 / 资源计划”
   - 需要确认是并列领域，还是同一领域下的子域

4. 出口分层是否纳入正式清单
   - 例如 App、OpenAPI、InnerAPI
   - 需要确认是算业务结构，还是只作补充说明

5. 子域是否继续下钻
   - 当子域已经足够具体时，需要确认是否还要展开到能力层

6. 产品命名与实现命名不一致
   - 需要确认最终文档使用的正式业务名称

## 推荐输出顺序

按以下顺序与用户协作：

1. 输出候选一级领域
2. 等用户确认一级领域
3. 逐个领域分析候选子域
4. 一个子域分析完后，开始能力分析，如果子域已经足够具体，向用户确认是否分析能力。
5. 遇到新旧并存或边界冲突时先提问
6. 最后再整理成汇总版清单

## 推荐输出格式

### 一级领域阶段

```markdown
- XXX
  描述：一句话说明该领域解决什么业务问题。
```

### 子域阶段

```markdown
- XXX
  描述：一句话说明该子域的职责边界。
```

### 能力阶段

```markdown
- XXX
  描述：一句话说明该能力提供的业务价值。
```

### 用户确认问题阶段

```markdown
需要确认：

1. XXX 和 XXX 是否属于升级替代关系
2. XXX 是否仍纳入正式结构
3. XXX 和 XXX 是并列领域还是子域关系
```

## 最终产物要求

最终产物应满足：

- 结构清晰
- 命名统一
- 不混用技术分层和业务分层
- 明确哪些是正式结构，哪些是历史兼容
- 明确哪些层级停在子域，哪些继续下钻到能力
- 每一层都有一句话描述
